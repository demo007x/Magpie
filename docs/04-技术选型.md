# 技术选型 · 决策记录（ADR）

> v0.1 · 2026-09 · 记录"为什么是它"，供未来回顾与翻案

## ADR-01 跨平台框架：Tauri 2 ✅

- **结论**：Tauri 2（Rust 核心 + 系统 WebView），UI 层 React + Vite + TypeScript
- **理由**：7×24 后台常驻工具，内存是硬指标（Electron 常驻 200~400MB 不可接受）；系统级能力（鼠标钩子/AX/无框窗口）本就需要原生代码，Rust 直达；Tauri 2 稳定且支持双窗口/透明/置顶/Channel 流
- **否决**：Electron（体积/内存）、Flutter Desktop（系统级能力弱）、双原生（人力×2）

## ADR-02 语言分层：Rust 系统层 + TS AI 编排层 ✅

- **结论**：划词捕获、窗口管理、存储、SSE 传输在 Rust；动作注册表、prompt、流式渲染、未来 agent 在 TS（WebView 内）
- **理由**：Rust AI 生态薄（2026-09 调研：Rig ~6.7k stars / genai 0.5.x / Swiftide 活跃 / **langchain-rust 维护时断时续不采用**），而 AI 功能迭代最快，应放在生态最厚的 TS 侧；Rust 只守契约面窄且五年不变的部分
- **否决**：全 Rust 自建 agent（逆生态风口）、Python sidecar（分发噩梦）、AI 逻辑全进 Rust

## ADR-03 MVP 传输：Rust SSE 哑管道 ✅（非浏览器直连）

- **结论**：`ai_chat` 命令 = Rust reqwest 流式转发 OpenAI 兼容 SSE，经 Tauri Channel 推给 TS
- **理由**：BYOK 场景下任意第三方端点大概率无 CORS 头，WebView 直连不可靠；管道 ~100 行、协议（chat/completions）多年稳定、对框架零依赖
- **翻案条件**：M2 引入 Vercel AI SDK 时，优先评估其自定义 transport 复用本管道 / `plugin-http` 直连流式，若成立可精简
- **修订（2026-10-21）**：管道已长出厂商适配（Responses 形态 / thinking 参数注入 / 4xx 重试），"哑"改指"不做 AI 逻辑与 prompt 编排"——那仍在 TS 层

## ADR-04 AI 框架策略：热路径零框架，分层引入 ✅

- **结论**：MVP 不引入任何 AI 框架（prompt 模板 + 流式管道即可）；M2 浅 agent（搜索/问答）引 **Vercel AI SDK**；M4 深度研究模式按需拉起 **deepagents**（Node sidecar）
- **修订（2026-09-19）**：原结论中"RAG（M3）用 Rust sqlite-vec 自建管道"随自建知识库方向一并否决——M3 改为统一动作模型（自定义 AI 动作 / 接入动作 / workflow），见 [01 §6](./01-产品定位与规划.md)
- **理由**：见 [03-模块设计 §C.6](./03-模块设计.md)；消费级划词工具 90% 场景为浅任务（≤5 次工具调用），框架收益为负（延迟/体积/调试复杂度）
- **背景**：曾评估 LangChain（重、抽象厚）与 deepagents 做核心（长任务错配、双语言栈），均否决为"地基"，保留为"可选挂件"

## ADR-05 文本捕获：无障碍 API 优先 + 兼容模式兜底（2026-09 修订）✅

- **结论**：macOS CGEventTap + AX 为主路径；原「全流程不读/写剪贴板」红线修订为**常开的兼容模式兜底**——AX 全链路失败时，模拟 ⌘C 读剪贴板并自动还原快照
- **修订理由**：实测微信 4.x（Qt 自绘）AX 取词不可行；生态同证（Easydict [issue #84](https://github.com/tisfeng/Easydict/issues/84) 将微信/Pages/Keynote/Word 列为 AX 取词失败应用，官方解法即模拟 ⌘C 白名单）。「划词比无痕更重要」，照抄行业通行解，无开关、常开兜底
- 详见 [03-模块设计 §A.3.3](./03-模块设计.md)

## ADR-06 浮动条定位：跟随鼠标上方（2026-09-22 二次修订）✅

- **结论**：胶囊水平中心对光标、卡片底边距光标上方 **16px**（业界弹出层间距惯例 12–16px；实测 12px 距离光标过近易误触，取上限），屏顶放不下翻到光标下方。所有应用统一此行为，不区分取词路径。
- **修订理由（贴选区方案的实测翻案）**：曾实现 AX `BoundsForRange` 选区锚定（垂直贴选区上方、水平钳制在选区内），实测发现问题——① Chromium/Electron 系应用（Chrome / VSCode / ZCode 等）普遍不暴露选区几何（`AXBoundsForRange` 支持不一致是 [Chromium 官方承认的已知挑战](https://chromium.googlesource.com)），导致"部分应用贴选区、部分应用跟光标"的双轨体验分裂；② 贴选区在多行长选区时胶囊跳到首行上方，离拖选终点（用户注意力所在）反而更远。豆包等主流划词工具实测即"跟随鼠标上方"，视觉上与"选区上方"无异（单行选区时光标就在选区行内）。**业界同类（Easydict / PopClip）取不到选区几何时同样降级鼠标位置**——本方案等于把降级位升级为唯一定位，行为可预期、实现简单、全应用一致。
- **历史**：v0.1 初版为"光标右下优先 + 翻转"；2026-09-22 上午改为"AX 选区锚定优先 + 光标兜底"；同日实测后定为"统一跟随鼠标上方 12px"。
- **附带修复（保留）**：范围回退路径的 AXValue 类型常量错位（`kAXValueCFRangeType` 误写为 3，实为 4；3 是 CGRect）——该 bug 使微信等 Qt 自绘应用的"AXSelectedTextRange + StringForRange"取词路径从未生效，一直静默滑落兼容模式。修正后该路径恢复工作。

## ADR-07 密钥存储：MVP 明文 JSON，M2 迁 keyring ⚠️

- **结论**：`settings.json` 明文存 Key（与主流 BYOK 工具现状一致），设置页明示用户；M2 迁系统钥匙串（`keyring` crate），`settings.rs` 预留迁移位
- **风险**：设备被物理访问时 Key 可读——对 MVP 种子用户（极客）可接受

## ADR-08 Windows 文本捕获：UI Automation + WH_MOUSE_LL 低级钩子 ✅（2026-10-15）

- **结论**：Windows 划词捕获 = UI Automation（uiautomation-rs）+ `WH_MOUSE_LL` 低级钩子，闸门体系（起点分类/应答证据）与 macOS 对位；一卡一窗拓扑（分离卡）
- **细节**：见 `capture/windows.rs` 头注释与 [03 §A.7](./03-模块设计.md)（分离卡拓扑见 §B.1.1）
