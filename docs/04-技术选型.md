# 技术选型 · 决策记录（ADR）

> v0.1 · 2026-09 · 记录"为什么是它"，供未来回顾与翻案

## ADR-01 跨平台框架：Tauri 2 ✅

- **结论**：Tauri 2（Rust 核心 + 系统 WebView），UI 层 React + Vite + TypeScript
- **理由**：7×24 后台常驻工具，内存是硬指标（Electron 常驻 200~400MB 不可接受）；系统级能力（鼠标钩子/AX/无框窗口）本就需要原生代码，Rust 直达；Tauri 2 稳定且支持双窗口/透明/置顶/Channel 流
- **否决**：Electron（体积/内存）、Flutter Desktop（系统级能力弱）、双原生（人力×2）

## ADR-02 语言分层：Rust 系统层 + TS AI 编排层 ✅

- **结论**：划词捕获、窗口管理、存储、SSE 传输在 Rust；动作注册表、prompt、流式渲染、未来 agent 在 TS（WebView 内）
- **理由**：Rust AI 生态薄（2026-09 调研：Rig ~6.7k stars / genai 0.5.x / Swiftide 活跃 / **langchain-rust 维护时断时续不采用**），而 AI 功能迭代最快，应放在生态最厚的 TS 侧；Rust 只守契约面窄且五年不变的部分
- **否决**：全 Rust 自建 agent（逆生态风口）、Python sidecar（分发噩梦）、AI 逻辑全进 Rust

## ADR-03 MVP 传输：Rust SSE 哑管道 ✅（非浏览器直连）

- **结论**：`ai_chat` 命令 = Rust reqwest 流式转发 OpenAI 兼容 SSE，经 Tauri Channel 推给 TS
- **理由**：BYOK 场景下任意第三方端点大概率无 CORS 头，WebView 直连不可靠；管道 ~100 行、协议（chat/completions）多年稳定、对框架零依赖
- **翻案条件**：M2 引入 Vercel AI SDK 时，优先评估其自定义 transport 复用本管道 / `plugin-http` 直连流式，若成立可精简
- **修订（2026-10-21）**：管道已长出厂商适配（Responses 形态 / thinking 参数注入 / 4xx 重试），"哑"改指"不做 AI 逻辑与 prompt 编排"——那仍在 TS 层

## ADR-04 AI 框架策略：热路径零框架，分层引入 ✅

- **结论**：MVP 不引入任何 AI 框架（prompt 模板 + 流式管道即可）；M2 浅 agent（搜索/问答）引 **Vercel AI SDK**；M4 深度研究模式按需拉起 **deepagents**（Node sidecar）
- **修订（2026-09-19）**：原结论中"RAG（M3）用 Rust sqlite-vec 自建管道"随自建知识库方向一并否决——M3 改为统一动作模型（自定义 AI 动作 / 接入动作 / workflow），见 [01 §6](./01-产品定位与规划.md)
- **理由**：见 [03-模块设计 §C.6](./03-模块设计.md)；消费级划词工具 90% 场景为浅任务（≤5 次工具调用），框架收益为负（延迟/体积/调试复杂度）
- **背景**：曾评估 LangChain（重、抽象厚）与 deepagents 做核心（长任务错配、双语言栈），均否决为"地基"，保留为"可选挂件"

## ADR-05 文本捕获：无障碍 API 优先 + 兼容模式兜底（2026-09 修订）✅

- **结论**：macOS CGEventTap + AX 为主路径；原「全流程不读/写剪贴板」红线修订为**常开的兼容模式兜底**——AX 全链路失败时，模拟 ⌘C 读剪贴板并自动还原快照
- **修订理由**：实测微信 4.x（Qt 自绘）AX 取词不可行；生态同证（Easydict [issue #84](https://github.com/tisfeng/Easydict/issues/84) 将微信/Pages/Keynote/Word 列为 AX 取词失败应用，官方解法即模拟 ⌘C 白名单）。「划词比无痕更重要」，照抄行业通行解，无开关、常开兜底
- **Windows 对位（2026-11-19 修订）：同一个兜底，但改为按应用授权的允许清单，默认绝不发按键**。三条差异决定了不能照搬"常开"：① macOS 能问出「聚焦的是哪个应用、是不是编辑器家族」（NSWorkspace + bundle id），Windows 侧只能拿到进程路径，无法探测目标应用此刻处于什么界面——同一个 Zed，编辑区里 Ctrl+C 是复制、集成终端里是给子进程发中断信号，杀伤性动作不能在无法分辨时自动发生；② 自绘应用（实测 Zed Windows 版整棵 UIA 树只有顶层 Window 一个节点）本身没有任何可探测的选区状态，兜底成败只能交给用户的观察；③ 提权应用受 UIPI 屏障，注入按键同样打不进去，常开只会白按。触发条件收紧为「两条 UIA 父链都没有任何 TextPattern 层 + 应用在名单内 + 剪贴板不是文件或图片」，剪贴板快照还原的竞态规则与 macOS 同源。**翻案条件**：若有了可靠的「当前界面是否终端」探测手段（如按焦点元素/控件类型判定），且实测误伤为零，可考虑对无文本接口应用转为常开
- **发现流程（2026-11-19 补充）**：闸门保留、默认值不变，改的是「用户怎么知道这里有道开关」——同一应用第三次走到「两条父链都无 TextPattern 层」且未授权时，用 **4 秒定时 toast** 提示一次去哪开启（阈值 3 次：1 次会被「随手拖滚动条」触发；每应用只提示一次：这个分支处在鼠标松开的检测线程上，没有标记就变成每次划词失败都弹）。**不用 sticky toast**：它没有自动隐藏，指引会一直挂在那里碍眼——真机实测正是这样暴露的；同批给 toast 补上了「点一下即收场」（`dismiss_toast`：窗口不抢焦点但照常收点击，与胶囊同一机制；进度条类型不响应——点掉它并不会让正在跑的识别停下来）。文案只负责指路（两行：读不到 + 去哪个卡片加），不在 toast 里讲利害关系，也不放一键授权按钮。**只提示、不代授权**——授权所需的说明必须在设置页那段完整文案里读到，不能被一条几秒的 toast 替他改配置
- **否决（2026-11-19）：全局常开兼容取词**。提案依据是实测「Zed / 微信 / 终端里都能出胶囊，且没发生中断」，但该测试集不含风险状态：终端里 Ctrl+C 杀伤的前提是此刻有前台进程在跑，空提示符无论测多少次都不会命中；且触发条件是「拖拽手势 + 应用不暴露文本接口」，画布类拖拽（图片编辑框选 / CAD 框选 / 白板 / 游戏视角）同样满足，而那些应用里 Ctrl+C 绑定成什么完全未知——可能复制对象、可能应用自定义的停止或取消。「默认关闭 + 按应用授权」是知情同意立场，不是可测出来的性能参数，故维持；将来若有了可靠的界面类型探测再按上面的翻案条件重议
- **已决（2026-11-19）：主键改为 Ctrl+Insert，Ctrl+C 退为兜底**。用户探针实测 Zed / 终端 / Chrome / VS Code 四家 Ctrl+Insert 均命中，「换键会不会把功能做成永远取不到词」这个顾虑被证伪；收益是本 ADR 最痛的那条残余风险（Ctrl+C 在终端里中断正在运行的进程）在主流应用里走不到。代价与边界照旧要认：① 主键不认的应用仍会发 Ctrl+C，风险只是收窄而非消除（叠加条件＝主键无绑定 + 此刻终端里有前台进程）；② 兜底判定用「剪贴板相对快照变了」，分不清「键未绑定」与「复制结果与原内容相同」，所以最坏情况是白按一次主键再多等 600ms；③ 主键本身在个别应用里可能绑成别的功能（传统控件里 Ctrl+Insert 就是复制，但自绘应用的 keymap 各写各的）——这仍是允许清单默认关闭的理由，不是可以常开的理由。实测数据缺失的应用按 ② 处理：取不到词、无副作用
- 详见 [03-模块设计 §A.3.3](./03-模块设计.md)（macOS）、[§A.7](./03-模块设计.md)（Windows）

## ADR-06 浮动条定位：跟随鼠标上方（2026-09-22 二次修订）✅

- **结论**：胶囊水平中心对光标、卡片底边距光标上方 **16px**（业界弹出层间距惯例 12–16px；实测 12px 距离光标过近易误触，取上限），屏顶放不下翻到光标下方。所有应用统一此行为，不区分取词路径。
- **修订理由（贴选区方案的实测翻案）**：曾实现 AX `BoundsForRange` 选区锚定（垂直贴选区上方、水平钳制在选区内），实测发现问题——① Chromium/Electron 系应用（Chrome / VSCode / ZCode 等）普遍不暴露选区几何（`AXBoundsForRange` 支持不一致是 [Chromium 官方承认的已知挑战](https://chromium.googlesource.com)），导致"部分应用贴选区、部分应用跟光标"的双轨体验分裂；② 贴选区在多行长选区时胶囊跳到首行上方，离拖选终点（用户注意力所在）反而更远。豆包等主流划词工具实测即"跟随鼠标上方"，视觉上与"选区上方"无异（单行选区时光标就在选区行内）。**业界同类（Easydict / PopClip）取不到选区几何时同样降级鼠标位置**——本方案等于把降级位升级为唯一定位，行为可预期、实现简单、全应用一致。
- **历史**：v0.1 初版为"光标右下优先 + 翻转"；2026-09-22 上午改为"AX 选区锚定优先 + 光标兜底"；同日实测后定为"统一跟随鼠标上方 12px"。
- **附带修复（保留）**：范围回退路径的 AXValue 类型常量错位（`kAXValueCFRangeType` 误写为 3，实为 4；3 是 CGRect）——该 bug 使微信等 Qt 自绘应用的"AXSelectedTextRange + StringForRange"取词路径从未生效，一直静默滑落兼容模式。修正后该路径恢复工作。

## ADR-09 实体提取：AI 语义优先 + 确定性兜底 ✅（2026-10-23，翻案「实体零 AI」）

- **背景**：实体出口曾定调「零 AI、零外部 API」（entities.rs 头注释）。真机翻车：NSDataDetector 把日期区间拆碎、纯日期默认补 12:00、裸时间脱离日期语境解析成今天/明天——确定性组件无法理解上下文，这不是规则补丁能穷尽的
- **结论**：仅限「提取信息」面板（用户点击触发的冷路径）：已配置默认模型服务时，日期/地点等语义信息优先由 AI 按固定 JSON 结构返回（区间合并、裸时间挂靠日期、阶段名作标题、纯日期全天）；AI 失败/零结果/未配置时整组回落 NSDataDetector/NLTagger/正则。链接/邮箱/电话/验证码始终过正则校验（AI 召回的也必须原文照抄才算数）
- **边界**：划词热路径（胶囊判断）零 AI 不变；AI 走 ADR-03 既有 SSE 哑管道，Rust 零改动；设置页「智能提取」总开关可关（settings.smartExtract）
- **实现**：`src/shared/aiExtract.ts`（prompt/解析校验）+ `floating/App.tsx` showExtractPanel（按组覆盖与兜底编排）

## ADR-10 朗读：本地 ONNX（Kokoro + sherpa-onnx）而非系统 TTS ✅（2026-11-10）

- **背景**：最初设想走系统 TTS（macOS `say` / AVSpeechSynthesizer）——零成本零依赖，但真机试听否决：系统中文音色机械感重，英文也不足以做学习材料。云端 TTS（CosyVoice2 等）音色最好，但把「朗读」变成需要 API Key 的联网功能，违背就地、离线的产品取向
- **结论**：本地神经网络 TTS。模型选 Kokoro-82M fp32（中英双语 103 音色，Apache-2.0），引擎用 sherpa-onnx 官方预编译 CLI，按需下载到应用配置目录（约 410MB 下载 / 590MB 落盘），推理走子进程。曾用 int8 量化版（140MB/344MB），真机对比英文音色塑料感明显、中文几乎无差，换回完整精度
- **理由**：① 音色质量明显优于系统 TTS 且完全离线；② 子进程隔离延续 OCR 的既有取向（onnxruntime 崩溃不伤主应用）；③ 不把 C++ 推理链编进二进制，CI 的编译/链接不受影响；④ 模型可商用
- **边界**：朗读目前是冷路径（设置页试听、结果窗朗读钮），不做流式；音色选择只暴露精选列表；macOS 与 Windows x64 均已接入（Windows 引擎 = sherpa-onnx win-x64 MD/Release 包，播放 = 系统 PowerShell SoundPlayer，无需第三方音频栈）
- **分发**：引擎与模型都在首次使用时从 GitHub Releases 下载，不随安装包分发——既控制体积，也避免把引擎包内的 espeak-ng 数据文件（GPLv3）当作应用的一部分再分发；解压用 Rust 侧 bzip2+tar crate，不依赖各平台系统解压命令

## ADR-11 更新分发：应用内自更新（updater 插件 + minisign + Release 静态清单 + 自签稳定签名）✅（2026-11-19，翻案「只提示不自更新」）

- **背景**：ADR 之外的原决策是「更新检测只做提示不自更新」，顾虑是 GitHub 匿名 API 60 次/小时限流与发布工程复杂度。用户侧两个真实痛点：每次发版都要去 Release 页手动下载安装包；安装新包后 macOS 三项授权（辅助功能/输入监控/屏幕录制）全部重置——TCC 授权锚定代码签名身份，ad-hoc 签名每个包身份都变，macOS 把每个新包当新应用
- **结论**：接入官方 `tauri-plugin-updater`，检测→弹窗确认→下载→替换→重启全程应用内完成。更新清单 `latest.json` 由 release.yml 发版时组装并挂到 Release，应用按固定静态地址拉取（`releases/latest/download/latest.json`），绕开匿名 API 限流（原顾虑不成立）。更新包经 minisign 验签（TAURI_SIGNING_PRIVATE_KEY secrets）；macOS 包用自签证书（Magpie Dev，CI 以 MACOS_CERTIFICATE secrets 注入同一张 10 年证书）稳定签名身份，授权跨版本保留。更新从不静默安装：发现新版事件 + toast 各提示一次，主窗口弹窗确认才下载（`update://progress`）；通用页「自动检查更新」开关只关后台检查
- **理由**：① 用户更新从「去网页下载安装」变成「点一下」，且授权不重置；② 全链路零费用（无 Apple Developer Program）；③ 验签防更新包被篡改；④ updater 全部 Rust 侧驱动，webview CSP 无需放行外部主机
- **否决**：纯前端热更新（Tauri 无官方机制，划词/窗口改动都在 Rust 层，覆盖面太小，且保不住授权）；公证（Developer ID $99/年，仅优化首次下载的 Gatekeeper 体验，非本决策范围，可后补）
- **风险**：① 更新私钥/证书泄露 = 可伪造更新分发，靠 secrets 保护，泄露后换钥重发；② 发版忘挂 latest.json → 更新检查静默失败，发版清单 ④ 核验兜底；③ 更新私钥体系启用前的老安装（≤0.1.23）最后一次更新仍需手动下载 + 重新授权，0.1.24 起闭环
- **边界**：每次更新仍是完整包（Tauri 包体积小，不做增量）；无公证，首次从官网下载仍被 Gatekeeper 拦一次；Windows 走 NSIS passive 更新，无授权重置问题；dev 构建不受影响（conf 的 ad-hoc 保留，CI 用 APPLE_SIGNING_IDENTITY 覆盖）

## ADR-12 离线词典：读用户已有词库，不自带、不下载 ✅（2026-11-19）

- **背景**：翻译动作此前全部依赖网络——AI（BYOK）或机翻厂商 API。查单词这类"有标准答案"的
  需求走生成式链路既慢又烧 token。社区开源词典 [Aictionary](https://github.com/ahpxex/Aictionary)
  的本地词库质量足够（84,212 条英→中词条，学习者向释义 + 用法辨析 + 双语例句 + 音标 + 词源，
  变形词各自独立成条故**无需词形还原**），且是标准 SQLite 文件，可直接读
- **结论**：Magpie 新增离线词典动作，**只读用户机器上已存在的词库文件**（设置页选路径 +
  自动探测兼容词典应用的默认位置），不随安装包分发、本版不内置下载器
- **理由**：
  - **许可**：Aictionary 代码 MIT，但词库数据是 [open-dictionary](https://github.com/ahpxex/Aictionary)
    （Wiktionary 快照 + 大模型补写）的 **CC BY-SA 4.0**——ShareAlike 使"裁剪/转换后的衍生库"
    必须以同等许可开放并署名。Magpie 整体是 MIT，读一个用户本机文件不产生分发行为；一旦把
    精简库打进安装器，就背上同等开放 + 署名的义务。与 ADR-10 把 espeak-ng（GPLv3）数据挡在
    包外同理
  - **体积**：单个词库文件 864MB，打进安装包不可接受（本项目对内存/体积一直是硬指标，见 ADR-01）
  - **复用**：装了兼容词典的用户零成本获得该能力
- **代价**：数据结构由第三方定义 → 启动时校验库内版本标记，不认识即整体降级为"词典不可用"
  而非猜测解析；该文件可能被词典应用并发写入（其日志模式非 WAL）→ 只读打开 + 忙等超时，
  取不到按未命中处理，绝不写该文件
- **署名义务**：即使不分发数据，界面与文档仍标注词库来源与授权方式——设置页「词典」
  卡片的「词典来源」一节（贴着功能本体，用户在开启处即看见）+ README「License」节的
  第三方数据声明。关于页暂未加通用致谢区（将来若为 TTS/OCR 等第三方组件增设，此处一并迁入）
- **翻案条件**：若"用户拿不到词库文件"成为主要流失原因，再评估 Magpie 侧独立下载器
  （复用 ADR-10 的按需下载范式，从上游 Release 取，仍不进安装包）；若上游许可变更为可
  自由再分发，则重新评估自带精简库
- **实现约束（踩过才写下来的）**：词库主索引是 `(语言码, 规范化词头)` 复合索引，
  **查询必须带语言码谓词**，漏掉即退化为全表扫描——实测单次查询从 32µs 恶化到 222ms
  （相差三个数量级）；词条表另有一份与规范化表内容重复的大字段（单条最大 35KB），
  取词只读规范化子表，不碰它
